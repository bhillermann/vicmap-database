## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Generation marker
- **D-78:** The proof that a published generation came from a given run is a **durable `vicmap_audit` row**, not a table `COMMENT` and not inference from staging-table absence. A new table `vicmap_audit.publication` is added to `db/provision_vicmap_loader.sql` (by-hand, superuser-provisioned exactly like `staging_validation` per D-70), with `vicmap_loader` granted `SELECT, INSERT` only, with no `UPDATE`/`DELETE`, matching the D-70 least-privilege posture. This matches PROJECT.md's "Postgres audit records govern idempotency". — **Reversibility:** costly — it is a new provisioned table that promotion writes and resume reads, and it needs a one-time operator re-run of the provisioning script plus a preflight extension.
- **D-79:** The publication row is **inserted inside the single promotion transaction** (`promote_order`), so the marker commits atomically with the `SET SCHEMA`/`RENAME`/`GRANT` and a rolled-back promotion leaves no marker. A failure to write it is a promotion failure (`pub_promotion_failed`), and rollback preserves the prior tables (PUB-03).
- **D-80:** Granularity is **one row per layer**, with primary key `(run_ts, manifest_digest, target_table)`, mirroring `vicmap_audit.staging_validation`. Resume uses the same subset logic as the D-68 gate: every manifest layer must have a publication row for this `(run_ts, manifest_digest)`.
- **D-81:** Each row records the **published table's identity (`pg_class` OID)** of `{publish_schema}.{target_table}` as it exists after the rename. Resume requires the live `vicmap.{target_table}` to exist with that same OID; an audit row alone is not enough. OIDs change on every publish (D-73), so this is a true generation id and catches an out-of-band replace or drop.
- **D-82:** Each row also records the facts needed to rebuild `PromotionResult` on resume: at least `server_version` (from promotion's `SELECT version()`) and `published_at` (server timestamp at promotion). A resumed run reconstructs `PromotionResult` from these durable rows rather than re-querying, so the summary describes the promotion that actually happened (consistent with D-76's re-read-durable-artifacts pattern).

#### Resume trigger & summary
- **D-83:** Resume is **auto-detected on a plain `publish_order.py` re-run**, with no `--resume` flag and no CLI surface change. The run classifies the order's state (D-86) and skips promotion when every layer is in the resumable case. This keeps a future unattended retry (OPS-05) flag-free.
- **D-84:** A resumed run is **visible in both outputs**. A new `ProgressEvent` (e.g. `publication_resumed`) goes on the JSON Lines stream, and `summary.json` gains a field recording whether this run performed or resumed the promotion (e.g. `promotion: "performed" | "resumed"`) plus the original `published_at`. The EVID-01 redaction rules still apply to the new fields. — **Reversibility:** reversible — `summary.json` lives in the git-ignored `runs/` tree and nothing else parses it yet.
- **D-85:** A re-run **after a fully successful run** (with `summary.json` already present) is handled as an ordinary resume. It re-runs the reader proof and the validation re-read against live state, replaces `summary.json` atomically, and exits 0. There is no special-casing of an existing file and no "already complete" failure. Because this makes `write_summary` a real overwrite path, the write must be atomic (write to a temp file in the same directory, then replace). This supersedes the Phase 4 note that a plain write is sufficient.

#### Ambiguous & legacy states
- **D-86:** Each manifest layer is classified before any DDL:
  - **A** — this run's staging table exists → normal promotion (today's path; replaces any live table per D-71).
  - **B** — staging table absent, publication row for this run exists, live OID matches → resumable.
  - **C** — staging table absent, publication row exists, live table missing or OID differs → superseded.
  - **D** — staging table absent, no publication row for this run → no provenance, which includes tables published before this fix.
  - **E** — layers fall in different cases (e.g. some A and some B) → inconsistent.

  Outcomes: the order promotes only when **all** layers are A, and resumes only when **all** are B. Any C → `pub_generation_superseded`. Any D, or E → `pub_generation_ambiguous`. Every fail-closed outcome issues **no `DROP` and no DDL**.
- **D-87:** There are **two new reason codes** at the `db_publish` stage. `pub_generation_superseded` means this run did publish, but the live table has since been replaced. Its remediation hint: nothing to resume, stage a fresh run. `pub_generation_ambiguous` means the live state's provenance can't be proven. Its remediation hint: inspect `vicmap`/`vicmap_audit`, then stage a fresh run. Both join the closed `ReasonCode`/`_FAILURE_POLICY` vocabulary in `vicmap_acquire/evidence.py` with secret-free hints.
- **D-88:** **No backfill** for the currently live `vicmap.vmadd_address`, which was published before any marker existed. Nobody hand-writes audit rows asserting provenance that can't be proven. Resuming an old run against it is case D and fails closed. The next normal publish from a fresh staging run (case A) replaces it and writes the first real marker.
- **D-89:** The **D-68 validation gate still runs first on every run**, whether promoting or resuming. A resumed run has exactly the same preconditions as a fresh one, and no path reaches a summary without PASS rows.

#### Post-commit failure boundaries
- **D-90:** Reads of `vicmap_audit` report at the **existing `db_audit` stage**. This covers resume detection (publication rows) and `read_layer_validations` (validation rows). A privilege denial stays `db_audit_privilege_denied`. Any other read failure, including a connection failure, uses a new `db_audit_read_failed`, and never `pub_promotion_failed`. These reads therefore must not go through a connection helper that maps connect errors to `PromotionFailed`.
- **D-91:** Summary assembly and writing (`assemble_summary`, `write_summary`) report at a **new `publication_summary` stage** with a new `pub_summary_failed` code, replacing the current fall-through to `internal_failure`. The success event keeps the name `publication_summary`; the planner confirms that a Stage value and the event name may share that string, or picks a distinct stage name.
- **D-92:** Afterwards, `pub_promotion_failed` is raised **only** from inside the promotion transaction: DDL, grant, publication-row insert, or the promotion connection itself. `verify_reader_access` keeps its existing `db_reader_verify` codes.

#### Testing & evidence
- **D-93:** Criterion 5 is proven **offline and live**. Offline tests use fakes that cover every classification case (A–E) and each post-commit boundary (D-90/D-91). The live test (a new `Live*` class following `_LivePublishMixin` in `tests/test_publish.py`/`tests/test_publish_order.py`) reproduces the 2026-09-24 incident. It publishes with `VICMAP_READER_PASSWORD` unset, which gives `reader_role_unavailable` after commit, with the staging table consumed and no `summary.json`. It then re-runs with the password set and expects exit 0, `summary.json` with `promotion: "resumed"`, and no promotion DDL issued. That live run is the evidence for marking WINDOWS.md #16 `fixed`.

## Summary

This phase closes WINDOWS.md #16, a real 2026-09-24 live incident: `publish_order.py`'s promotion commits durably (metadata-move `SET SCHEMA`/`RENAME`/`GRANT` inside one transaction), but a post-commit step (`verify_reader_access`) can still fail — e.g. `VICMAP_READER_PASSWORD` unset. Because the promotion already consumed the staging table (`ALTER TABLE ... SET SCHEMA` moves and renames it, it does not copy it), a naive re-run re-enters `promote_order`, which tries to `ALTER TABLE {staging}.{staging_table} SET SCHEMA ...` against a table that no longer exists there, and psycopg raises `UndefinedTable` — caught by the existing generic `except Exception: raise PromotionFailed()` in `_promote_layer`'s caller chain — so a purely cosmetic failure (missing reader password) is permanently misreported as `pub_promotion_failed`, and the run can never complete.

The fix has three parts, fully specified by CONTEXT.md's locked decisions: (1) a new durable per-layer marker (`vicmap_audit.publication`, one row per `{run_ts, manifest_digest, target_table}`, inserted inside the same promotion transaction, carrying the published table's `pg_class` OID plus `server_version`/`published_at`); (2) a five-way classification (D-86, cases A–E) run before any DDL on every invocation, deciding promote (all A), resume (all B), or one of two new fail-closed reason codes (`pub_generation_superseded`, `pub_generation_ambiguous`); (3) narrower failure-boundary reporting so a post-commit failure is never again reported as `pub_promotion_failed` — new `db_audit_read_failed` (detection/validation reads) and `pub_summary_failed` (summary assembly/write) reason codes, at a stage discipline that must not route through the connect helper (`_connect`) that currently maps every connection failure to `PromotionFailed`.

No new third-party dependency is introduced. This phase extends the same `vicmap_acquire.publish`/`vicmap_acquire.staging`/`vicmap_acquire.evidence`/`db/provision_vicmap_loader.sql` surface Phase 4 built, using the same psycopg 3.3.4 driver already vetted and pinned via nixpkgs, the same closed-reason-code/closed-stage vocabulary pattern, and the same `_LivePublishMixin` live-test fixture convention.

**Primary recommendation:** Add a classification step (`classify_publication_state` or similar) that runs immediately after the D-68 validation gate and before `promote_order`'s DDL, driven by three per-layer facts already obtainable from existing helpers — `staging.staging_table_name` + a catalog existence check, a `vicmap_audit.publication` row lookup, and a `pg_class` OID comparison against the live `vicmap.{target}` table — then branch `publish_order.main` to either call `promote_order` (case A) or reconstruct `PromotionResult` from the durable publication rows (case B) without touching DDL, using a **new, separate connect helper** for every detection/read path so a connection failure there can never resolve to `pub_promotion_failed`.

### Pattern 1: Per-layer classification before any DDL (D-86)

**What:** A pure decision function that, for one manifest layer, reads three independent facts (staging-table existence, publication-row existence, live-table OID match) and returns a closed case label, run for **every** layer before the order-level verdict is computed and before any DDL runs for **any** layer.

**When to use:** Every `publish_order.py` invocation, immediately after the existing D-68 gate (`assert_all_layers_validated`) and before `promote_order` is ever called.

**Example (staging-table existence probe, following the same `to_regclass` idiom the live test fixtures in `tests/test_publish.py` already use for schema/table existence checks):**

```python
# Source: pattern derived from tests/test_publish.py::_LivePublishMixin._ensure_audit_table
# (verified this session, lines 1054-1061) — to_regclass('schema.table') returns NULL
# for a table that does not exist, non-NULL (its OID) for one that does; this is the
# standard catalog-existence idiom already used elsewhere in this codebase's own tests.
cursor.execute(
    "SELECT to_regclass(%s)",
    (f"{staging_schema}.{staging_table}",),
)
(staging_oid,) = cursor.fetchone()
staging_exists = staging_oid is not None
```

**Example (live table OID comparison, D-81 — using the identical `pg_class`/`pg_namespace` join shape `_discover_constraints`/`_discover_indexes` already use for catalog discovery in `publish.py`):**

```python
# Source: pattern mirrors vicmap_acquire/publish.py::_discover_constraints
# (verified this session, lines 313-323) — same two-table catalog join idiom,
# reused for an OID lookup instead of a constraint list.
cursor.execute(
    "SELECT t.oid FROM pg_class t "
    "JOIN pg_namespace n ON n.oid = t.relnamespace "
    "WHERE n.nspname = %s AND t.relname = %s",
    (publish_schema, target_table),
)
row = cursor.fetchone()
live_oid = row[0] if row else None
```

### Pattern 3: Reconstructing `PromotionResult` from durable rows on resume (D-82, D-76's re-read-durable-artifacts pattern)

**What:** On the RESUME branch, `publish_order.main` must produce the same `PromotionResult(server_version, published_tables)` shape `promote_order` returns on the PROMOTE branch, but by reading the `vicmap_audit.publication` rows this order already wrote on its earlier (committed) run — never by re-querying `SELECT version()` live, which would describe *this* run's connection, not the promotion that actually happened.

**When to use:** Exactly once, on the RESUME branch, before `verify_reader_access` is called (which needs `published_tables`).

**Example:**

```python
# Illustrative only — column names are Claude's Discretion (D-78 "beyond the
# decided content"). Demonstrates the re-read-durable-artifacts shape D-76
# already established for read_layer_validations.
def rebuild_promotion_result_from_publication_rows(
    rows: tuple[PublicationRecord, ...],
) -> PromotionResult:
    server_versions = {row.server_version for row in rows}
    assert len(server_versions) == 1  # D-80: one row per layer, same run
    return PromotionResult(
        server_version=next(iter(server_versions)),
        published_tables=tuple(row.target_table for row in rows),
    )
```

### Anti-Patterns to Avoid

- **Inferring resumability from staging-table absence alone:** This is the exact anti-pattern WINDOWS.md #16 exposes — staging-table absence is consistent with "resumed", "superseded", and "never had provenance" (D-86 cases B, C, D) and cannot distinguish them. D-78 exists specifically to replace this inference with a durable, positively-checked marker.
- **Routing detection/audit reads through `publish._connect`:** Doing so re-creates the same misreporting bug this phase exists to fix, one level up — a transient connection blip during `read_layer_validations` or the new classification reads would still surface as `pub_promotion_failed` (D-90).
- **Backfilling `vicmap_audit.publication` for `vicmap.vmadd_address`'s current live generation:** D-88 explicitly forbids this. A hand-written row asserting provenance the system did not itself observe defeats the purpose of a durable audit trail; the correct next step for that specific table is a fresh case-A publish.
- **Treating a `pg_errors.IntegrityError`/duplicate-key on the publication-row INSERT as a soft no-op:** Unlike `staging.record_validation`'s `ON CONFLICT DO NOTHING` idiom (safe because a repeated staging validation write for the same key is definitionally identical), a repeated publication-row insert for the same `(run_ts, manifest_digest, target_table)` inside a **fresh promotion attempt** would only happen if classification already misjudged the layer as case A when a row existed — i.e., a bug in the classifier, not a benign retry. The insert should not silently swallow a conflict; let it raise into the transaction's rollback path as an ordinary `pub_promotion_failed`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Catalog existence check for a table by schema-qualified name | A `SELECT COUNT(*) FROM information_schema.tables WHERE ...` query or a bespoke `pg_class`/`pg_namespace` join written from scratch | `to_regclass('schema.table')` (already the idiom `_LivePublishMixin._ensure_audit_table` uses in this codebase, verified this session) | `to_regclass` is PostgreSQL's own built-in, search-path-aware, NULL-on-absence resolver — one function call, no join, no race between two separate `information_schema` queries |
| Object OID discovery for the "is this the same generation" check | String-comparing table names, or trusting `published_tables` from the caller's own in-memory result | A direct `pg_class`/`pg_namespace` OID lookup, exactly the join shape `_discover_constraints`/`_discover_indexes` already use in `publish.py` | OIDs are the only identity PostgreSQL itself guarantees changes on every `DROP`+recreate (D-73's existing "new OID per publish" finding) — a name match alone cannot detect an out-of-band replace |
| Atomic `summary.json` overwrite (D-85's new requirement) | A bespoke lock file or a `try`/`except FileExistsError` retry loop | The standard write-temp-then-`os.replace` idiom (`tempfile.NamedTemporaryFile(dir=run_directory, delete=False)` + `os.replace(tmp, final)`), matching the same-directory + atomic-rename requirement `manifest.py`'s `write_manifest` already established for a different file in this codebase (per D-85's own text: "write to a temp file in the same directory, then replace") | `os.replace` is atomic on POSIX (same filesystem, same directory avoids cross-device rename failure); a lock file or retry loop adds failure modes without adding atomicity guarantees `os.replace` already provides |

**Key insight:** Every mechanism this phase needs — catalog existence probes, OID lookups, atomic same-directory file replacement, closed reason-code vocabularies — already has a working precedent *inside this same codebase* (verified by `Read` this session in `publish.py`, `staging.py`, and the `_LivePublishMixin` test fixtures). The planner should treat "find the existing local idiom and reuse its shape" as the default move for every new piece of code this phase adds, rather than introducing a new pattern.

## Common Pitfalls

### Pitfall 1: The generic `except Exception: raise PromotionFailed()` swallows more than promotion errors

**What goes wrong:** `publish._connect` (verified `vicmap_acquire/publish.py:203-244`) and `promote_order`'s own `try`/`except Exception: connection.rollback(); raise PromotionFailed()` (lines 485-490) are both broad catches. Any new classification/detection code that reuses `_connect` — even for a pure read — will have its own unrelated failures (e.g. a transient network blip during the OID lookup) silently reclassified as `pub_promotion_failed`, reproducing exactly the misreporting bug this phase exists to fix, just relocated one call earlier.
**Why it happens:** `_connect` was designed and named for the promotion transaction specifically; it was never meant to be a general-purpose "any authenticated connection" helper, but its shape (timeout SETs, single connection) is generically reusable, inviting reuse without inviting a rename of its failure mapping.
**How to avoid:** Write classification/detection reads against a distinct connect path (Pattern 2) whose failure mapping is `db_audit_read_failed` (new) or `AuditPrivilegeDenied` (existing, reused per D-90), never `PromotionFailed`. Confirm this new path is not itself imported by `promote_order`.
**Warning signs:** A test asserting a connection-failure path returns `pub_promotion_failed` when the failing call is read-only and occurs before any DDL.

### Pitfall 2: `read_layer_validations` already shares `_connect` with `promote_order` — the same mismatch may already exist there

**What goes wrong:** Verified this session (`vicmap_acquire/publish.py:699`), `read_layer_validations` calls `_connect(policy, password)` — the identical helper `promote_order` uses. A connection failure during this post-commit, read-only call would today surface as `pub_promotion_failed`, even though the promotion transaction has already committed and this call touches no DDL. D-90 names `read_layer_validations` explicitly as one of the two calls (`db_audit` reads) that must report `db_audit_read_failed` on a non-privilege failure.
**Why it happens:** `_connect` was the only connection helper `publish.py` had; reusing it for a later read-only call was the path of least resistance when Phase 4 was written, and Phase 4's own tests never exercised a connection failure specifically during `read_layer_validations` (only during `promote_order`/`assert_all_layers_validated`).
**How to avoid:** The plan must route `read_layer_validations` through the same new non-`PromotionFailed`-mapping connect path as the new classification reads (Pattern 2) — this is not purely new code, it is also a fix to an existing call site.
**Warning signs:** Grepping `vicmap_acquire/publish.py` for `_connect(policy, password)` call sites after this phase's changes should show it used only inside `assert_all_layers_validated` (a pre-DDL gate) and `promote_order`/`_promote_layer` (the transaction itself) — not in any function whose failure should map to `db_audit_read_failed` or `pub_summary_failed`.

### Pitfall 3: The evidence-vocabulary "stays total" tests will fail until updated in lockstep

**What goes wrong:** `tests/test_evidence.py::EvidenceContractTest::test_every_reason_has_one_fixed_stage_and_remediation_hint` (verified this session, line 301) asserts **exact** equality between a hand-maintained `expected` dict and `evidence.reason_stage_vocabulary()`, and a second assertion that `set(expected.values()) == {stage.value for stage in evidence.Stage}` — every `Stage` member must be reachable. Adding 4 new `ReasonCode` members (`pub_generation_superseded`, `pub_generation_ambiguous`, `db_audit_read_failed`, `pub_summary_failed`) and 0–1 new `Stage` member (`publication_summary`, per D-91) without updating this test's `expected` dict will fail the whole-suite exact-equality check, not just a subset check.
**Why it happens:** This is a deliberate design choice (closed vocabulary, proven total by an exact-equality test) rather than an accident, but it means this phase cannot add a reason code "quietly" — the test file itself is part of the required diff.
**How to avoid:** Update `EvidenceContractTest.test_every_reason_has_one_fixed_stage_and_remediation_hint`'s `expected` dict (currently 54 entries, verified this session) to include the 4 new entries (58 total) and, if a new `Stage.PUBLICATION_SUMMARY` is added, confirm it appears in at least one entry's value (satisfying the "every Stage is reachable" half of the same test). A parallel `Phase4VocabularyTest`-style additive test (subset-check pattern, verified at line 1741) should be added for the 4 new codes, mirroring `Phase3VocabularyTest`/`Phase4VocabularyTest`'s own precedent.
**Warning signs:** `nix develop path:. -c python -m unittest tests.test_evidence -v` failing on `EvidenceContractTest` after adding the new `ReasonCode` members but before touching the test file.

### Pitfall 4: `write_summary` becoming a real overwrite path (D-85) changes its failure surface

**What goes wrong:** `write_summary`'s own docstring (verified `vicmap_acquire/publish.py:879-901`) currently states "a plain write... is sufficient; a retried publish simply overwrites it" and explicitly notes any `OSError` "propagates unwrapped... deliberately left for the CLI's catch-all `INTERNAL_FAILURE` mapping." D-85 supersedes this: the write must become atomic (temp file + replace) **and** D-91 gives it a dedicated `pub_summary_failed` code at a new `publication_summary` stage — so the old "let it fall through to `internal_failure`" behavior must be replaced, not merely made atomic.
**Why it happens:** The two decisions (atomic write, dedicated failure code) are easy to implement independently and forget to wire together — a planner or executor could add `os.replace`-based atomicity while leaving the exception path as a bare, unwrapped `OSError` that still falls through to `internal_failure`.
**How to avoid:** The plan should treat "atomic write" and "dedicated failure boundary" as one task, wrapping the temp-write/replace sequence's `OSError` (and `assemble_summary`'s `ValueError` on a malformed input, which is a `publication_summary`-stage failure too, per D-91's naming of both `assemble_summary` and `write_summary`) into the new closed exception whose `.code == "pub_summary_failed"`.
**Warning signs:** A test that induces an `OSError` during `write_summary` (e.g. read-only `run_directory`) and asserts the rendered failure's `reason` is still `internal_failure` instead of `pub_summary_failed`.

### Pitfall 5: `UndefinedTable` is the *symptom*, not the only failure the classifier must anticipate

**What goes wrong:** The live incident's proximate error was `psycopg.errors.UndefinedTable` from `ALTER TABLE {staging}.{staging_table} SET SCHEMA ...` against an already-consumed staging table. It would be tempting to "fix" this narrowly by catching `UndefinedTable` specifically inside `_promote_layer` and mapping it to a new code. This misses the actual requirement: D-86's classification must run **before** any DDL, for **every** layer, so that a mixed order (some layers case A, some case B — case E) is caught and fails closed with `pub_generation_ambiguous` rather than partially promoting some layers and hitting `UndefinedTable` on others mid-transaction.
**Why it happens:** Catching the specific driver exception at the point of failure is the smallest possible diff; building the full pre-DDL classifier is more code and touches the orchestration seam, not just `publish.py`.
**How to avoid:** Do not add `UndefinedTable` handling inside `_promote_layer`/`promote_order` as the fix. The classification step must be a distinct, earlier gate (mirroring how `assert_all_layers_validated` already runs before any DDL as a distinct gate) — `promote_order` should only ever be called once classification has already determined every layer is case A.
**Warning signs:** A plan task that modifies `_promote_layer`'s `except` clauses as its primary mechanism, rather than adding a new pre-gate function called from `publish_order.main` or from a wrapper `promote_order` calls before its transaction opens.

```python
# note). Demonstrates: same transaction as _promote_layer's DDL (no separate
# commit), OID read via the same catalog-join idiom _discover_constraints uses,
# server_version already available from promote_order's own "SELECT version()"
# (vicmap_acquire/publish.py:475-476, verified this session).
def _record_publication(
    cursor, *, run_timestamp, manifest_digest, target_table,
    publish_schema, server_version,
) -> None:
    cursor.execute(
        "SELECT t.oid FROM pg_class t "
        "JOIN pg_namespace n ON n.oid = t.relnamespace "
        "WHERE n.nspname = %s AND t.relname = %s",
        (publish_schema, target_table),
    )
    (published_oid,) = cursor.fetchone()
    cursor.execute(
        sql.SQL(
            "INSERT INTO {table} "
            "(run_ts, manifest_digest, target_table, table_oid, "
            "server_version, published_at) "
            "VALUES (%s, %s, %s, %s, %s, now())"
        ).format(table=sql.Identifier("vicmap_audit", "publication")),
        (run_timestamp, manifest_digest, target_table, published_oid, server_version),
    )
```

1. **Should `Stage.PUBLICATION_SUMMARY` be a new enum member, or should `pub_summary_failed` reuse an existing stage?**

   - RESOLVED (Plan 05.1-04): `staging.preflight_staging_privileges` is not extended; a promote verdict instead checks `has_table_privilege(current_user, 'vicmap_audit.publication', 'INSERT')` and fails closed with `db_audit_privilege_denied` before any DDL.

| A resumed run issuing a `DROP`/DDL against an ambiguous or superseded generation (destroying a table this run does not actually own the provenance of) | Tampering / Repudiation | D-86's fail-closed rule: every ambiguous or superseded outcome issues **no `DROP` and no DDL** — the classifier must gate all DDL, not just the `_promote_layer` drop statement, and this must be tested explicitly (not just asserted in the classification's return value) |
| An operator or a future caller hand-writing a `vicmap_audit.publication` row to force a resume against `vicmap.vmadd_address` (the table published before any marker existed) | Spoofing (of provenance) | D-88's explicit "no backfill" rule; enforced by the loader's `SELECT, INSERT`-only grant (no `UPDATE`, so an existing row can never be edited to match a new OID) and the fact that `INSERT` alone cannot retroactively prove a marker was written *inside* a real committed promotion transaction — this is a process control (documented in D-88), not a database-enforced one, and the planner should confirm the audit trail (`recorded_at`, `published_at`) plus the OID/server_version fields give an operator enough evidence to detect a suspicious row by inspection |
| A privilege-denied vs. a generic-failure read on `vicmap_audit.publication` being conflated, masking a provisioning gap as a transient error (or vice versa) | Information Disclosure (of the wrong failure cause) / Repudiation | D-90's explicit split: `db_audit_privilege_denied` (existing, reused) for `InsufficientPrivilege` specifically, `db_audit_read_failed` (new) for everything else — mirrors the existing `assert_all_layers_validated`/`read_layer_validations` pattern (`except pg_errors.InsufficientPrivilege: raise AuditPrivilegeDenied()`, verified this session) and must be extended identically to the new classification reads |
