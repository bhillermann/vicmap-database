<objective>
Prove one digest-verified manifest layer travels the whole new stack — config, manifest read,
connection, privilege proof, `ogr2ogr` load, row-count check, operator output — and then make
the privilege proof real.

Purpose: This phase's architectural risk is concentrated in one place: a Python process that
must hand a geodatabase to an external C++ loader, against a live database it does not own,
without ever touching production. Every layer of that path is new to this codebase. Proving it
end to end on one thin slice means a dead end costs one commit instead of six.
Output: `vicmap_acquire/staging.py`, the `stage_order.py` CLI, the operator's provisioning
script, and the live-database test classes — all skip-not-fail.

This plan fixes contracts 03-05 and 03-06 extend and must not rename: `StagingPolicy`'s field
names, the staging failure class names, `staging_table_name`'s output shape, and
`run_staging`'s signature.
</objective>

## Flagged planner assumptions (spec-less edge probe, DB-01 and DB-02)

The deterministic edge probe classified `DB-01` and `DB-02` as **`unclassified`**. Per protocol
an unclassified row is never auto-resolved with a backstop, so both are carried here as explicit
flagged assumptions rather than silently dropped. Neither is a blocker; each is a judgment the
operator should confirm at verification time.

| Requirement | Probe status | Planner assumption being made |
|---|---|---|
| DB-01 | `unclassified` — **UNRESOLVED, flagged** | Assumed that "verify its non-secret identity" is satisfied by printing the six D-61 fields once, and that no boundary case exists around a server that answers `version()` but has no PostGIS extension — this plan treats that case as `PostgisUnavailable`, a hard stop, rather than a partial identity. If the operator intends a PostGIS-less server to be reportable rather than fatal, this assumption is wrong. |
| DB-02 | `unclassified` — **UNRESOLVED, flagged** | Assumed that "the required privileges" means exactly: `USAGE` and `CREATE` on the staging schema, the ability to create a typed-geometry table and a GiST index there, the absence of `CREATE` on `public`, and a non-superuser role. Phase 4's own grants (reader role, publish-schema promotion) are deliberately out of scope here even though D-59 gives the role ownership of both schemas. If DB-02 was meant to preflight Phase 4's privileges too, this assumption is wrong. |

## Research pitfalls this plan implements against

| Pitfall | Effect on this plan |
|---|---|
| **3 — `has_table_privilege` raises on a table that does not exist** | Every staging table is, by D-48, one that has never existed. The preflight therefore checks `has_schema_privilege` (valid pre-creation) **and** runs a real rolled-back `CREATE TABLE` probe, never `has_table_privilege` against a staging table name. |
| **4 — `ogr2ogr -progress` is a terminal bar** | No stdout scraping anywhere. Progress is per-layer only, emitted by the calling Python around each subprocess (03-06). `-progress` is not passed. |
| **Anti-pattern — exit-code sub-typing** | `ogr2ogr` exits `1` uniformly on every failure kind. One fixed `LoadFailed` / `db_load_failed`; never a reason table keyed on exit code, never a branch on stderr content. |
| **Anti-pattern — string-formatted identifiers** | Every schema and table name reaching SQL goes through `psycopg.sql.Identifier` composition. No f-string SQL anywhere in `staging.py`. |

## Trust Boundaries

| Boundary | Description |
|---|---|
| `manifest.json` → `ogr2ogr` argv | Layer names and dataset paths that originated in an untrusted delivery become subprocess arguments and a PostgreSQL table name. |
| shell environment → subprocess environment | The one credential in this phase crosses into a child process; argv is world-readable through `ps`, environment is not. |
| Python → PostgreSQL | Schema and table identifiers reach SQL text; the loader role's grants are the only thing standing between staging and production. |
| geodatabase bytes → GDAL → PostgreSQL | A large C++ library parses untrusted binary input and writes rows directly through `COPY`. |
| PROJ coordinate operation → stored geometry | The transform chosen at load time decides whether stored coordinates are accurate or silently shifted. |
