# Phase 05.1 Plan 03: Resumed-run visibility, atomic summary overwrite, closed summary boundary Summary

**A resumed publish is now visible on both the event stream and in `summary.json` (promotion/published_at), a re-run after success is a safe repeatable resume via an atomic `write_summary`, and every summary-step failure reports `pub_summary_failed` instead of falling through to `internal_failure`.**

## Accomplishments

- `assemble_summary`'s summary gains a `"published_at"` field (D-84) — the original promotion's own timestamp, rendered through `evidence._require_utc_timestamp` as a UTC ISO-8601 string with a fixed six-digit microsecond field, lossless against PostgreSQL `timestamptz`. `PromotionResult.__post_init__` now also rejects a naive `published_at` at construction, mirroring the same check.
- `publish_order.py` emits `ProgressEvent.publication_resumed` on the JSON Lines stream immediately after `promote_or_resume` resumes and before the reader proof runs; a performed promotion still renders only `publication_summary`.
- Live proof (`LivePublishOrderResumeTest.test_rerun_after_post_commit_reader_failure_resumes`) now drives a full third run after the second's successful resume: run 2 asserts the `["publication_resumed", "publication_summary"]` event order and that `summary["published_at"]` equals the durable marker's own `published_at`; run 3 proves a re-run after a fully successful run is itself an ordinary, repeatable resume — same two events, one publication row, the published table's `(oid, xmin)` still unchanged, `_promote_in_transaction` patched to explode if reached in both runs.
- `write_summary` is now atomic (D-85): a same-directory `tempfile.NamedTemporaryFile`, flushed and fsynced, then `os.replace`-d over `summary.json`, with the run directory itself fsynced afterward via a new private `_fsync_directory` copy (mirroring `manifest.py`'s own documented convention). Any failure before the replace completes best-effort unlinks the temp file and raises `PublicationSummaryFailed`, leaving a prior `summary.json` byte-identical.
- `assemble_summary` and `summary_to_publication_event` now wrap their entire bodies so any non-`PublishFailure` exception — a malformed input, a missing provenance sidecar (`ProvenanceUnavailable`), a `KeyError` from a malformed summary dict — becomes the closed `PublicationSummaryFailed` at the `publication_summary` stage (D-91), never a raw exception and never the CLI's generic `internal_failure`. The CLI-level regression proves the real `write_summary` against a nonexistent run directory reports `pub_summary_failed`, then a follow-up run against a real directory completes the summary with a plain re-run.
