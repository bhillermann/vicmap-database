## Warnings

### WR-01: `promote_order` can raise a raw, unclosed `ValueError` instead of a `PublishFailure` for a zero-layer manifest

**File:** `vicmap_acquire/publish.py:944-998` (`_promote_in_transaction`), `vicmap_acquire/publish.py:174-207` (`PromotionResult.__post_init__`)

**Issue:** `_promote_in_transaction` initializes `published_at: datetime | None = None` (line 961) and only assigns it inside the per-layer loop (`if published_at is None: published_at = layer_published_at`, lines 980-981). If `manifest.layers` is empty, the loop body never runs, `connection.commit()` succeeds on a no-op transaction, and the function falls through to `return PromotionResult(..., published_at=published_at, promotion=PROMOTION_PERFORMED)` at line 993 — **outside** the `try/except` block that maps every other failure in this function to the closed `PromotionFailed`. `PromotionResult.__post_init__` (added by this phase) now rejects a non-timezone-aware value, so `published_at=None` raises a bare `ValueError` that is *not* a `PublishFailure`, escapes `_promote_in_transaction` and `promote_order` uncaught, and is only caught by `publish_order.py`'s generic `except Exception` fallback as `internal_failure` — never the more specific, boundary-accurate reason the rest of this phase is built to guarantee ("every failure must be reported at its true boundary," per `05.1-CONTEXT.md`'s phase boundary statement).

This exact path is unreachable through the CLI today: `publish_order.py` calls `promote_or_resume`, not `promote_order` directly, and `classify_publication_state`/`order_verdict` already fail closed with `PublicationAmbiguous` for an empty `target_tables` tuple before any promotion connection opens (verified by `FailClosedNoDdlTest.test_empty_target_set_fails_closed`). However, `promote_order` is still a public, directly-callable function whose docstring explicitly states it "stays callable directly... so existing callers... are unaffected" — this phase leaves a latent regression in that compatibility surface, and there is no test anywhere (`PromotionCompositionTest`, `PromotionRollbackCompositionTest`, etc.) that exercises `promote_order`/`_promote_in_transaction` with an empty manifest to catch it.

**Fix:** Either guard `_promote_in_transaction` against an empty `manifest.layers` before opening a connection (raising the same closed failure the D-68 gate would already produce for an empty `target_tables` set), or wrap the final `return PromotionResult(...)` construction in the existing `try/except Exception: raise PromotionFailed() from None` block so a `PromotionResult` construction failure is never allowed to surface as a raw `ValueError`:

```python
    finally:
        connection.close()

    try:
        return PromotionResult(
            server_version=server_version,
            published_tables=tuple(published),
            published_at=published_at,
            promotion=PROMOTION_PERFORMED,
        )
    except ValueError:
        raise PromotionFailed() from None
```

### WR-02: No advisory locking or generation fencing around classify-then-promote — a genuine, currently-open TOCTOU window

**File:** `vicmap_acquire/publish.py:592-707` (`classify_publication_state`), `vicmap_acquire/publish.py:1044-1092` (`promote_or_resume`)

**Issue:** `promote_or_resume` reads the order's state (staging-table OIDs, publication markers, live-table OIDs) on one short-lived connection (`classify_publication_state`), closes it, and only then opens a second, independent connection to actually run `_promote_in_transaction` (or, on `RESUME`, returns a purely in-memory result with no re-check at all). Nothing prevents a second `publish_order.py` invocation for the same `(run_ts, manifest_digest)` from running concurrently and observing the same `STAGED` classification, so two processes could both attempt `_promote_layer`'s `DROP TABLE IF EXISTS` + `SET SCHEMA`/`RENAME` against the same staging table at the same time — one succeeding, one failing with a generic, unclassified DDL error (correctly mapped to `PromotionFailed`, so no silent corruption, but the "closed" story that no ambiguous state is possible is not fully true under concurrency).

This is explicitly out of scope per `05.1-CONTEXT.md`'s `<deferred>` section ("Concurrent publish runs / advisory locking around classify + promote... belongs with OPS-05 unattended scheduling"), so I am not marking it a blocker for this phase. Flagging it here so it is visible in the review record rather than only in the planning doc, since the phase's own framing ("Ambiguous states fail closed... issue no DROP or other DDL") could otherwise be read as a stronger guarantee than the code actually provides once two operators (or a retry storm) run the CLI at the same time.

**Fix (for the deferred OPS-05 work, not this phase):** an advisory lock (`pg_try_advisory_lock` keyed on `(run_ts, manifest_digest)` or the order id) held for the duration of classify+promote, or acquired at the start of `promote_or_resume` and released in a `finally`.

### WR-03: `PromotionResult.__post_init__`'s timezone-aware check duplicates `evidence._require_utc_timestamp` instead of calling it

**File:** `vicmap_acquire/publish.py:198-207`, `vicmap_acquire/evidence.py:559-568`

**Issue:** `publish.py` already imports `evidence` (`from vicmap_acquire import download, evidence, staging`, line 84), so `PromotionResult.__post_init__`'s bespoke re-implementation of the "must be a timezone-aware `datetime`" check —

```python
if (
    not isinstance(self.published_at, datetime)
    or self.published_at.tzinfo is None
    or self.published_at.utcoffset() is None
):
    raise ValueError("published_at must be a timezone-aware datetime")
```

— is a literal copy of the guard clause inside `evidence._require_utc_timestamp` (`vicmap_acquire/evidence.py:566`). The docstring even says "validated identically to `evidence._require_utc_timestamp`," acknowledging the duplication. If a future change tightens or loosens the timezone-awareness contract in one location (e.g., to also reject a suspiciously far-future/past timestamp, or a different epoch bound), it is easy to update only one of the two copies and have them silently diverge.

**Fix:** call `evidence._require_utc_timestamp(self.published_at)` and discard the string result (or expose a small `evidence.require_timezone_aware(value)` predicate both call), rather than re-deriving the check by hand a second time.

## Info

### IN-01: `PublicationClassification.cases` is populated and returned but has no production consumer

**File:** `vicmap_acquire/publish.py:265-274`, `vicmap_acquire/publish.py:656-671`, `vicmap_acquire/publish.py:705-707`

**Issue:** `classify_publication_state` builds a `cases: list[LayerCase] = []` per manifest layer (lines 656-671) and returns it as part of `PublicationClassification` (line 706-707), but `promote_or_resume` (the only production caller) only ever reads `.verdict` and `.records` from the returned object (lines 1086-1091) — `.cases` is otherwise referenced only from tests (`ResumeReconstructionTest` et al. construct fixtures, but no test or production code reads `classification.cases` off a real `classify_publication_state()` return value either). This isn't wrong, just a write-only field today.

**Fix:** either surface the per-layer case breakdown somewhere operator-visible (e.g., in a future diagnostic event, since it would be genuinely useful for debugging a `CONFLICTED`/mixed-case `AMBIGUOUS` outcome), or drop the field until something consumes it, per "dead code" hygiene.

### IN-02: `vicmap_audit.publication` carries no `CHECK` on `table_oid`/`server_version`/`published_at` beyond `NOT NULL`

**File:** `db/provision_vicmap_loader.sql:83-92`

**Issue:** The new table's columns are typed correctly and covered by the PK, but there is no defense against, e.g., an `INSERT` racing with a concurrent `DROP`/reuse of the OID space producing a `table_oid` of `0` (the well-known "invalid OID" sentinel) ever being written — `_record_publication`'s `RETURNING`-driven insert already guards against "row not found" (raises `PromotionFailed`), but a `CHECK (table_oid > 0)` at the schema level would make the invariant "this OID always identifies a real relation" enforced by the database itself rather than solely by the Python call site, consistent with this codebase's general preference for provable, server-side guarantees (e.g., the `has_table_privilege` precheck, `RETURNING`-driven inserts elsewhere). Low priority — OID `0` from `pg_class.t.oid` in the exact join this statement uses is not a realistic outcome.

**Fix:** optional `CHECK (table_oid > 0)` if the team wants schema-enforced belt-and-suspenders; not required for correctness today.
